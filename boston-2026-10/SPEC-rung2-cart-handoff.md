# boston-2026-10 — rung 2: a pre-filled cart through the store's tag container. CONTRACT, draft

**Written 2026-09-27. Planned, not started**: it waits on the Owner confirming, at the 2026-10-01 meeting,
that the store's admin exposes a Google Tag Manager container field. Until then rung 1's links stand.

## 0. After this lands, what regenerates it, and from what?

| | what | where | regenerated by |
|---|---|---|---|
| the week's picks (Chef's Choice) | INPUT | `data/picks/<sunday-date>.json` — meal names and counts per plan | a person, weekly, from the Owner's picks |
| the links | OUTPUT | `dist/` | `npm run build` — each result card links to `…/order?mpid=N#fitaf=<payload>` |
| the tag | OUTPUT | `dist/gtm/fitaf-handoff.js` — pasted into a GTM **Custom HTML** tag | `npm run build`; its source is `src/gtm/` |

## 1. The shape

1. The microsite links to `https://fitafnutrition.com/order?mpid=<N>#fitaf=<payload>`. The part after `#`
   never leaves the visitor's browser, and nothing in the store reads it (every query parameter the
   store reads was listed on 2026-09-27; none is a cart).
2. **Without the tag, the link is exactly rung 1** — the plan's order page. The hand-off can only add.
3. **With the tag**, on a page load carrying `#fitaf=`: validate the payload, fill the cart (§ 2), remove
   the fragment, and open `/checkout`. **Any failure: remove the fragment and stop** — the visitor is on
   the plan's order page, as in rung 1. The tag must never leave a half-filled cart.
4. The payload is **meal names and counts, a plan, and an optional offer code** — no prices, no internal
   ids, no personal data. It is short enough for a QR code only if it is a key into a table the tag holds;
   otherwise it is carried by the microsite's link, not the printed code.

## 2. ⛔ The fork: how the tag fills the cart

| | **A — write the store's storage** | **B — press the store's own buttons** |
|---|---|---|
| how | build the cart lines and write `hmp_local_cart` (and `hmp_order_cart_coupon_codes`), then open `/checkout` | wait for the order page to render its meal cards, then use the page's own add controls for each named meal and count, then open `/checkout` |
| needs from us | each line's internal fields — product id, the size add-on ids (Lean `10538`, Signature `10539` in the 2026-09-27 sample), `mpid`, a local id | only meal **names** as the page shows them |
| prices | we must write them, and they must match the store's | ⭐ the store computes them, as for any shopper |
| breaks when | the store changes its storage shape | the store changes its page structure |
| detecting a break | compare the lines we wrote with what the page then shows | a named meal is not found on the page |
| recommendation | | ⭐ **B**: it uses the store's own rules, and it never writes a price. A is the fallback if B's timing proves unreliable |

The offer code, in either case: enter it through the page's own coupon field if one is available before
checkout; write `hmp_order_cart_coupon_codes` only if not — to be proven (§ 4).

## 3. The tag's own rules

- It acts **only** on a `#fitaf=` fragment, on the order page, and **only once** per load. On every other
  page it does nothing — it runs on every page of the store, checkout included.
- It sends **nothing** anywhere and loads nothing else.
- It is under 5 KB, has no dependencies, and is readable: a reviewer can check it in a minute.
- The container it lives in: access limited to named people, two-factor login, and **publishing needs a
  second person's approval** where the account allows it.

## 4. What must be proven, in one browser, with the Advisor watching — nothing submitted

1. The admin's GTM field exists, and the container loads on `fitafnutrition.com`.
2. B: the named meals are found and added at the right size and count; the sidebar and `/checkout`
   agree with the payload. A (if needed): a written cart survives the store's start-up.
3. The offer code applies and the store shows the discount.
4. A payload naming a meal that is not on this week's menu fails safe: no cart change, plain order page.
5. A visit with no fragment is untouched (the tag does nothing).

## 5. Tests — in `node --test`, no network

Payload encode/decode round trip; rejection of a malformed or oversized payload; for B, a fixture DOM of
the order page (saved from a public render) in which the named meals are found, and a mutant fixture
with one meal renamed, in which the tag refuses and changes nothing.

## 6. Amendment, 2026-09-29 — the store's own Custom Scripts, not a tag container; both fills behind one switch

**Found 2026-09-29**: the store's admin has a **Custom Scripts** page. It injects text into the storefront's `<head>`,
right after `<body>`, or right before `</body>`, *"exactly as supplied"*, on every page. So **no Google Tag Manager
container is needed**, and § 4's check 1 no longer applies. **Ruled by the Advisor the same day**:

1. **The tag becomes a script pasted into the Footer slot** (before `</body>`), after the page's own content, so it
   costs the first paint nothing.
2. **Both fills are built, behind one switch** (`FILL = "A"` or `"B"` at the top of the script). A run in one browser
   picks which one ships (item 6 below). § 2's recommendation of B stands until that run.
3. **The source lives here**: `src/storefront/fitaf-handoff.js`, built by **`npm run build:storefront`** to
   **`dist-storefront/`** (git-ignored; the production build's `dist/` is untouched), headed by a **version line**: the
   repository commit and a SHA-256 of the script text, so what is live can be compared with what is kept.
   ⚠ **Amended at the build, 2026-09-29**: both fills in one pasted text measured 5,930 bytes, over § 3's 5 KB. So
   **each built file carries ONE fill**: `fitaf-handoff.html` (the Footer block, the fill `FILL` names; B by default)
   and `fitaf-handoff.fill-A.console.js` / `fitaf-handoff.fill-B.console.js` for the one-browser run. The source keeps
   both fills and the switch; changing the shipped fill is a commit and a rebuild. The limit holds on every file.

**Rules added to § 3**:

- **No fragment: one check, then return.** A page without `#fitaf=` costs one read of `location.hash`: no storage
  read, no timer, no listener, no request. A test proves it with a stub window whose storage and timers throw if touched.
- **Once per load**: a marker on `window` stops a second run (the store's single-page navigation must not re-trigger it).
- **One guard around everything else**: any exception removes the fragment and stops, leaving the plan's order page as
  rung 1 leaves it. Never a half-filled cart: a fill that cannot complete every line changes nothing.
- ⛔ **The kill switch is deleting our block from the Footer.** It is never the store's *"Inject these scripts"*
  switch, which stops every vendor's script at once.

**The payload** (`#fitaf=` + base64url of JSON, version 1): `{ "v": 1, "mpid": <number>, "items": [{ "name": <meal
name as the page shows it>, "qty": <number>, "pid": <product id, A only> }], "code": <offer code, optional> }`. Refused
if it does not parse, is over 2 KB, has an unknown `v`, or has no items; an item's `qty` is a whole number from 1 to 21.

**A, what it writes** (the shape of a real cart line, supplied by the Advisor on 2026-09-27): `localId` (fresh),
`productId`, `quantity`, the three price fields in cents, `name`, `itemData` (the portion), `extensions.mpid` and
`cartItemData.mpid`, and `hmpAddons` (`addon_field_id 1297`; option `10538` Lean, `10539` Signature, ⬜ Performance
not yet known). ⚠ The prices written are the plan's per-meal price from the store's meal-plans page. Whether the store
recomputes them when it syncs the cart is one of the things the one-browser run shows.

**B, what it does**: on `/order?mpid=<N>`, wait (bounded) for the meal cards to render, find each payload meal **by its
name as shown**, press the card's own add control `qty` times, check that the page's cart shows every line, then open
`/checkout`. A meal not found means **no presses at all**: the check runs over every item before the first press.

**§ 4 is superseded by the plan's two stages** (the Advisor's; recorded in Fit AF's own records):

## 8. Amendment, 2026-09-29 — fill B ends by pressing the store's own CHECKOUT, never by loading `/checkout`

nothing. It never loads `/checkout` itself and never writes storage. The fragment is removed before the press.

## 11. Amendment, 2026-09-29 — the short link, a longer wait after CHECKOUT, and the size ceiling (the Advisor's rulings)

**Rulings** (the Advisor, 2026-09-29): the link shrinks by fingerprinting each meal (*"(A) is good."*); *"We can go up to
10k for the footer. 5k is a good target, but it's OK if we're above it slightly."*; and hardening continues (*"The more
we can harden, the better."*). **No link has been published**, so payload v1 (base64 JSON) is **retired, not kept
alongside**: only the Advisor's test links used it.

1. **The payload, version 2.** The fragment stays `#fitaf=` (an unambiguous key: a bare `#f=` could be another script's,
   and fill B removes the fragment it reads). Its value is ASCII, dot-separated:
   `2.<meal>[.<meal>…][.~<code>]`, where each `<meal>` is `<key>` or `<key>*<n>` (`n` 2–21, one item per meal as in v1),
   and `~<code>` is the optional offer code (`[A-Za-z0-9-]{1,40}`, still checked and not applied). **The plan's id is
   read from the page's own `?mpid=`**, once (v1 carried it twice). Example, the 7-meal Lean link:
   `https://fitafnutrition.com/order?mpid=21#fitaf=2.t1fkl.8avab.ihshe.1i5s0.tyv72.rgr2m.6uf54` (the keys illustrative).
2. **A meal's key**: 32-bit FNV-1a over the UTF-8 bytes of the meal's name **as the page shows it** (whitespace
   collapsed and trimmed, exactly as fill B reads a card's title), written in base 36, and **its last 5 characters**
   (the value modulo 36⁵). **One function, one source**: the link tool and the script use the same code (inlined in
   the build, as the plan counts are).
3. **Matching**: fill B keys every meal card's title and presses the card whose key matches. **Two cards on the page
   sharing a key that the link names ⇒ refuse the link, nothing pressed** (`stopped: two meals share a key`); a key
   matching no card ⇒ § 6's `not on this page`, naming the key. The full-plan rule (§ 7) and § 10 are unchanged.
4. **The wait after CHECKOUT is 30 s** (150 polls of 200 ms), after one live phone-width run of four stopped at 10 s with
   the store still committing (the live-test record § 12). The waits before a press stay at 10 s.
5. **The size**: the build **warns** above 5,120 bytes and **refuses** above 10,240, over each whole built file.
6. **The link tool** (`npm run handoff:link`) takes meal names as before and prints the v2 link, **with the names beside
   their keys**, so a person can read a link.
