## 1. What the visitor does

After choosing a plan (rung 1), a **"Claim your Boston offer"** section with the v0.2 wording
(`consent/DRAFT.md` § 1):
- **Email** — *we'll email you a unique code* · **Mobile number** — *enter your number so we can text you
  a unique code* · at least one is required; the form says so.
- **Delivery ZIP** — required.
- **First name** — optional.
- **Two unticked boxes**, "Email me" and "Text me" (with its full disclosure). Neither is required.
- **Claim my offer** → a confirmation view: *"Check your email / phone for your code."*

The page keeps the chosen plan in the URL fragment as today; the form submits the plan with the claim.

## 2. The endpoint — `POST /api/claim`

- The same Worker serves the static page and `/api/*` (assets first; `/api/*` to the Worker script).
- **Validation, refusing with a named 400**: at least one of email / mobile; email syntax; a US mobile
  number normalised to E.164; a five-digit ZIP; plan and count from the plan table; consent values
  exactly `true`/`false`; the wording version the page sent must be a version the Worker knows.
- **Bot protection**: Cloudflare Turnstile (invisible). Development uses Cloudflare's published **test
  keys**, which always pass.
- **Rate limit**: per IP, a small number of claims per hour (a Workers rate-limit binding or equivalent).
- **Returns** `{ ok: true }` only. ⛔ **Never echoes a code, a stored value or an id** — the code is
  delivered by email or text, not to the page.
- ⛔ **The IP address is used for rate limiting and not stored.**

## 3. The record — minimum, and built to be destroyed

Table **`claims`** (one row per claim):

| column | notes |
|---|---|
| `claim_id` | random, opaque |
| `event_id` | e.g. `boston-2026-10` |
| `plan`, `meals_per_week` | from the plan table |
| `offer_code` | ⭐ **unique, random, unguessable** (e.g. 8 chars from an unambiguous alphabet) — this is the **attestation token** (§ 5) |
| `created_at` | UTC |
| `export_state` | `pending` · `exported` · `purged` |

Table **`contacts`** (the PII — **separate, so it can be dropped whole**), keyed by `claim_id`:

| column | notes |
|---|---|
| `email`, `mobile_e164`, `first_name`, `zip` | as given |
| `consent_email`, `consent_sms` | booleans |
| `consent_wording_version` | e.g. `v0.2-draft` — the exact text shown |
| `consent_at` | UTC |

⛔ No IP, no user-agent, no location beyond ZIP, no plan "goal", nothing about health.

## 4. The purge — a first-class operation, tested now

`scripts/purge.mjs` (and the same logic callable from the Worker, later): for every claim whose
`export_state = 'exported'`, **delete its `contacts` row** and set `purged`. A dry-run mode prints counts
only. ⭐ **Tested against the dummy database now**, so destroying PII is a rehearsed operation and not
a hopeful one.

## 5. ⭐ The attestation token — the offer code

After the purge, the only thing linking a person to the event is the **offer code** they hold. If they
order and redeem it, the order carries the code, and the code carries the event — **no hash of their
email, nothing re-linkable held by us**. This needs the store to accept a pool of unique codes (asked at
the 2026-10-01 look at the store's backend). **If it cannot**, the fallback is a keyed hash of the
normalised email — which is **pseudonymous, not anonymous**, and would have to say so in the privacy
notice.

## 6. ⛔ Consent evidence outlives the database

When a contact is exported to Mailchimp, its **consent fields travel with it** (`consent_email`,
`consent_sms`, `consent_wording_version`, `consent_at`, `event_id`) — because once this database is
purged, Mailchimp holds the only copy, and proof of consent for marketing texts must outlive the sending.
The export is a later rung; this rung defines the fields so nothing has to be reconstructed.
